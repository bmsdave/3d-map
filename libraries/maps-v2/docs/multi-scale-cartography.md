# Многомасштабная картография: что об этом известно

Свод исследования по тому, как современные карты управляют детализацией.
Собран не по нашему коду, а по спецификациям (Google, Yandex, Mapbox/MapLibre,
OGC, OpenMapTiles) и научным работам по generalization, multi-scale
representation и label placement.

Держится в репозитории, потому что меняет несколько наших решений, а не только
объясняет чужие. Что именно меняет — в конце; правки, адресованные v1, ушли в
[`parity-plan.md`](../../maps/docs/parity-plan.md), правки v2 внесены в
[`ROADMAP-rebuild.md`](../../../ROADMAP-rebuild.md).

**Отношение к остальным документам.** Документ живёт в `maps-v2/docs` и
действует для v2; упоминания `Band { from_zoom, to_zoom }`, `max_per_tile` и
«задач плана» ниже относятся к v1, где теория впервые сверялась с кодом.
[`zoom-and-layers.md`](../../maps/docs/zoom-and-layers.md) (v1) — наблюдение:
что видно на экране Google Maps на z3/z6/z12/z17 и чем плохи наши линии. Этот
документ — теория под тем же вопросом. Наблюдение и теория сошлись в главном
выводе, и это добавляет ему веса.

## Зум — не таблица «уровень → список слоёв»

Главная ошибка модели, которую мы неявно исповедуем: «для каждого зума есть
список типов объектов». Реальная архитектура — конвейер из пяти независимых
LOD-систем:

```
Spatial LOD  →  Geometric LOD  →  Semantic LOD  →  Symbolic LOD  →  Label LOD
   какой          какая              какие            как             какие
   кусок          геометрия          объекты          рисовать        подписи
```

Наша `Band { from_zoom, to_zoom }` покрывает только **Semantic LOD**, и то
частично. Остальные четыре у нас либо отсутствуют, либо схлопнуты в пайплайн.

### Spatial LOD — какой кусок пространства

Пирамида тайлов. При росте `z` на единицу линейное разрешение удваивается,
число тайлов растёт как `4^z`. Google документирует схему 256×256 и деление
1×1 → 2×2 → 4×4; Yandex описывает практически ту же модель и прямо приводит
`4^z`.

Стандартизировано это лучше, чем принято думать: OGC API Tiles определяет
**Tile Matrix Set** — набор регулярных сеток для разных масштабов и CRS. То есть
XYZ/Web Mercator — это де-факто промышленный *профиль* более общей модели, а не
единственный возможный стандарт.

**Практическая деталь, которая нас касается:** Yandex по умолчанию использует
**эллипсоидальный** Mercator, сферический получается при нулевом эксцентриситете.
Мы всюду считаем сферический. Если когда-нибудь придётся сводить данные с их
тайлами — это расхождение в координатах, а не в форматах.

### Geometric LOD — какая геометрия

Один объект не обязан иметь одну геометрию. Темза на обзорной карте не должна
нести все меандры:

```
мастер-геометрия  50 000 вершин
   ↓
z6    120 вершин
z10   800
z14   5 000
z18   исходная
```

Классика — **Douglas–Peucker (1973)**: убрать точки полилинии, сохранив форму в
пределах допустимой геометрической ошибки. У нас это есть
(`simplification_tolerance(tile_zoom)`).

Чего у нас нет — современного варианта: **LOCALIS** (Amiraghdam, Diehl,
Pajarola, 2019) выбирает LOD динамически по **screen-space error**, вместо
хранения нескольких дискретных геометрий. Это ровно тот же приём, что LOD в 3D.

### Semantic LOD — какие объекты

Самая интересная часть. В центре Лондона на z15 кандидатов в POI — тысячи.
Правило `zoom >= 15 → показать POI` бессмысленно.

**Jiang, Liu, Jia (2011)** формализовали это через heavy-tailed распределения:
в географическом пространстве всегда много мелких объектов и мало крупных.
Генерализация — это сохранение «головы» распределения и агрегация или удаление
«хвоста». Удивительно хорошо ложится на современный POI ranking.

Отсюда форма, которой у нас нет вообще:

```
importance(feature) = класс + значимость + население
                    + ранг дороги + известность POI + контекст
```

### Symbolic LOD — как рисовать

Векторный тайл говорит, **что существует**; стиль решает, **как показать**.
Mapbox/MapLibre Style Spec задаёт `minzoom`, `maxzoom`, фильтры, source-layer,
layout и paint, плюс zoom-выражения для интерполяции.

Один тайлсет порождает совершенно разные карты. У нас цвет запечён в пакет —
см. задачу 3 плана.

### Label LOD — какие подписи

Отдельная оптимизационная задача, и очень тяжёлая.

## Генерализация — это не только «упростить»

Классическая теория даёт десять операций, а не одну:

```
selection → simplification → smoothing → aggregation → amalgamation
→ collapse → displacement → exaggeration → classification → typification
```

Самое полезное для архитектуры: **LOD может менять не только количество
геометрии, но и её тип и семантику**.

```
небольшая река:   полигон → линия → исчезает
вокзал:           пути + платформы + здания → полигон → иконка → ничего
десять зданий:    десять упрощённых полигонов → один полигон застройки
```

Наш `to_zoom` — это только `selection`. Ни `aggregation`, ни `collapse`,
ни `typification` у нас нет.

**Shea & McMaster (1989)** — фундаментальная модель «когда и как
генерализовать». **Feng, Thiemann, Sester (2019)** и **Zhou et al. (2023)**
показывают ML-подходы к генерализации зданий.

## Сколько объектов оставлять

### Töpfer's Radical Law

Классический ответ: при уменьшении масштаба количество сохраняемых объектов
должно снижаться закономерно, а не произвольно. Современные работы по
multi-scale mapping продолжают использовать это как отправную точку.

**Это прямо касается нашего `max_per_tile: Some(48)`.** Я записал в
`parity-plan.md`, что порог «ставился замером — менять его тоже замером». Это
верно, но недостаточно: у величины есть закон, а не только эмпирика.

### Настоящая единица бюджета — экран, а не объекты

И вот здесь исследование **опровергает нашу модель напрямую**.

Ограничивающий ресурс — не число объектов на квадратный километр, а
**количество визуальной информации на площадь экрана**:

```
не   features / tile          ← у нас так
а    screen-space occupancy   ← правильно
```

Одна крупная подпись «London» занимает столько же графического пространства,
сколько пять мелких POI. Постоянное число объектов на тайл поэтому не является
достаточной метрикой качества.

Оговорка в пользу нашего решения: production-тайлеры всё равно применяют
feature-density как **эффективную аппроксимацию** — Mapbox документирует
ограничение плотности точек для POI-слоёв именно ради места под подписи. То есть
`max_per_tile` — не ошибка, а приближение, и знать это стоит.

**Gedicke et al., «Zoomless Maps» (2020)** рассматривают ровно эту проблему для
мобильных: зум сам по себе плохо решает clutter, потому что увеличение масштаба
одновременно уничтожает географический контекст.

## Подписи — NP-трудная задача

Здесь лежит огромная часть сложности Google Maps.

MapLibre прямо сообщает, что символы могут быть скрыты вследствие коллизии
текста или иконки; через API можно получить объекты, которые существовали в
данных, но были исключены рендерером именно из-за коллизии. Есть отладочная
визуализация collision boxes, и подписи плавно появляются и исчезают после
перерасчёта размещения.

```
данные есть
    ↓ стиль говорит «видимо»
    ↓ зум говорит «видимо»
    ↓
коллизия подписей
    ↓
НЕ НАРИСОВАНО
```

Это объясняет знакомое поведение: сдвинул карту на несколько пикселей — и
появилось название, которого не было.

**«Three Rules Suffice for Good Label Placement»** отмечает, что нахождение
максимального по размеру набора непересекающихся подписей — **NP-трудная**
задача. Поэтому production-системы используют эвристики, приоритетное
упорядочивание и пространственные индексы, а не глобальный оптимум.

**Harrie et al. (2022)** показывают, что плотность, истинная геометрия подписи и
связи «иконка ↔ текст» остаются сложными и сегодня.

### Следствие, которое ломает наши тесты

**Видимость объекта — не функция от `feature × zoom`. Она зависит от viewport.**

```
visibility = f(scale, importance, geometry, style,
               viewport, конкуренты, размер подписи, коллизии, контекст)
```

После панорамирования на несколько пикселей подпись может исчезнуть или
появиться, потому что изменился набор коллизий.

У нас есть e2e-тесты вида «объект X виден на z14». Как только появятся подписи
и коллизии, такие утверждения станут **флаки по своей природе**, а не по
случайности. Формулировать их придётся иначе — через кандидатов и ранг, а не
через факт отрисовки.

## Генерализовать по одному объекту нельзя

**Simultaneous Graphic Generalization of Vector Data Sets** предлагает
рассматривать генерализацию как общую задачу оптимизации: объекты нельзя
генерализовать независимо, потому что изменение одного создаёт или устраняет
конфликты с соседями.

```
расширили символ дороги      → конфликт с соседними зданиями
сдвинули подпись дороги      → нужно сдвинуть другую подпись
упростили границу области    → должна остаться топологически согласованной
                               с соседней границей
```

Это принципиальное предупреждение для задачи 2 плана: расширение таксономии до
сорока классов, сделанное «по классу за раз», породит конфликты, которых сейчас
нет просто потому, что классов пять.

## Три разных зума

Терминология, которой нам не хватало, когда делали фолбэк:

```
source zoom   — до какого уровня реально нарезаны тайлы
style zoom    — против какого числа вычисляются правила стиля
camera zoom   — где стоит камера прямо сейчас
```

Overzoom — это когда `camera zoom` ушёл глубже `source zoom`, и рендерер тянет
геометрию из тайлов максимального имеющегося уровня. Мы это реализовали
(`select_covered_tiles`), но три величины не различали и называли всё «зумом».

## Что это меняет у нас

| Находка | Что правит |
|---|---|
| Пять LOD-систем вместо одной таблицы | рамка всего плана; наша `Band` — только Semantic LOD |
| Бюджет — площадь экрана, а не число объектов | `max_per_tile` — приближение, а не метрика; знать предел |
| Töpfer's Radical Law | у порога 48 есть закон, а не только замер |
| Heavy-tail / head-tail selection | основа для `importance()` в задаче 2 |
| `minzoom` — только eligibility gate | после него нужен ranking, иначе на z14 вываливаются все POI |
| Генерализация — совместная оптимизация | предупреждение для расширения таксономии |
| Видимость зависит от viewport | наши e2e-утверждения про видимость станут флаки |
| source / style / camera zoom | терминология для overzoom |
| Yandex — эллипсоидальный Mercator | если когда-нибудь сводить данные |
| LOCALIS: screen-space error | альтернатива дискретным LOD в задаче 1 |

## Формула, к которой всё сводится

```
RenderedMap(view) = Optimize(
    Importance(features),
    Fidelity(features),
    VisualClarity(view),
    Context,
    Performance
  | scale, viewport, style)
```

Карта — результат ограниченной оптимизации, а не выборка из базы. Зум лишь
меняет ограничения задачи. Система постоянно решает, что оставить, что
упростить, что агрегировать, что подчеркнуть и что скрыть, чтобы количество
воспринимаемой информации оставалось управляемым.

**Одной фразой:** архитектурный стандарт современной карты — пирамида тайлов +
многомасштабные векторные представления + стиль, зависящий от масштаба +
ранжирование по значимости + оптимизация по площади экрана + разрешение
коллизий подписей. Не фиксированная таблица объектов на каждый зум.

## Открытый стек, если аналитика поверх карты

Отдельная тема, записана здесь же, чтобы не потерялась. Актуальная связка для
платформы «карта + аналитика по локациям»:

| Слой | Инструмент | Зачем |
|---|---|---|
| Хранение и пространственные запросы | **PostGIS** поверх PostgreSQL | источник истины |
| Генерация векторных тайлов из PostGIS | **Martin** (Rust) | быстрый тайл-сервер |
| Рендер базовой карты | **MapLibre GL JS** | форк Mapbox GL без лицензионных ограничений |
| Аналитические слои поверх | **deck.gl** | heatmap, hexbin, GPU-визуализация больших датасетов |
| Пространственная индексация | **Uber H3** | агрегация по гексагонам вместо точек |
| Локальная аналитика без сервера | **DuckDB + DuckDB-Spatial** | большие выгрузки |

Живой пример всего вместе — GeoLibre (MapLibre + deck.gl + DuckDB-WASM). На этой
же связке построены Kepler.gl и CARTO.

**Как это соотносится с нами.** Мы пишем собственный рендерер на Rust/wasm, а не
берём MapLibre — это осознанное продуктовое решение, и стек выше его не
отменяет. Но три вещи из него применимы прямо:

- **H3** — если аналитика по районам появится, гексагональная агрегация решает
  ту же задачу, что `london:zone:cell-rNcM` в нашем пакете, но стандартно и
  совместимо с чужими инструментами.
- **PostGIS + Martin** — альтернатива нашему офлайновому пайплайну для случая,
  когда данные меняются часто, а не собираются из датированного снапшота.
- **MapLibre остаётся эталоном для чтения** независимо от того, используем мы
  его как библиотеку или нет — см. `zoom-and-layers.md` §8b.
