# Производительность лаборатории

Как измерить, где студия проводит время, и что означают числа, которые
печатает `npm run test:perf`.

## Что считается бюджетом

**Ни один кусок работы не держит main thread дольше 10 мс.** Именно это
делает слайдер тягучим: сеть, ждущая триста миллисекунд, не блокирует
ничего, а одно декодирование на сорок миллисекунд роняет три кадра.
Стена — от движения ручки до правильного кадра — измеряется и
записывается, но не проверяется: зум в незагруженный уровень не успеет
скачать, проверить и декодировать тайл за десять миллисекунд, и
требовать этого значит держать красным то, с чем никто не может ничего
сделать.

| бюджет | что |
|---|---|
| 10 мс | худший одиночный блокирующий вызов за взаимодействие |
| 10 мс | p95 `render()` на неподвижной камере |
| ≤1 | планов резидентности на кадр |
| без роста | удерживаемые тайлы и байты при повторе того же движения |

## Фазы

Хост размечает свои вызовы к SDK — за границей wasm профилировщик
браузера видит один вызов и не знает, во что тот превратился.

| фаза | что это | блокирует |
|---|---|---|
| `render` | кадр целиком, внутри рендерера | да |
| `decode` | `load_tile`: тайл превращается в меши и подписи | да |
| `demand` | план резидентности: что показать, что подвезти, что выгнать | да |
| `debug` | снятие отладочного состояния (карточки зовут его на каждое событие) | да |
| `labels` | диагностика подписей | да |
| `clamp` | возврат камеры на землю пакета | да |
| `fetch` | сеть | нет |
| `digest` | SHA-256 через `crypto.subtle` | нет |
| `pass` | весь проход загрузки, стена | нет |
| `blocked` | та часть прохода, что держала поток | сумма |

Разбивку кадра по слоям (`ground`, `fills`, `roads`, `buildings`,
`labels`, `residency`) считает сам рендерер и отдаёт в `debug()`.

## Посмотреть своими глазами

```
http://localhost:5178/?perf=overlay#/card/roads-micro
```

Оверлей поверх сцены: во что обошёлся кадр, сколько хост держит тайлов,
сколько планов построено. Работает на любой студии.

`?perf=1` включает только трассу, без оверлея — оверлей опрашивает
`debug()` каждый кадр, и во время замера это была бы работа, добавленная
измерением. Ровно так меряют e2e-тесты.

Из консоли:

```js
window.__maps2Perf.enable();   // если открыто без ?perf
window.__maps2Perf.reset();    // обнулить перед движением
// ... подвигать
window.__maps2Perf.log();      // таблица по фазам + худший блок
window.__maps2Perf.worstBlock();   // { phase, ms }
window.__maps2Perf.longFrames();   // длинные кадры глазами браузера
```

Те же интервалы попадают в запись Performance в DevTools под именами
`maps2:<фаза>` — записывать отдельно ничего не нужно.

## Прогон

```sh
npm run test:perf                       # все студии
npm run test:perf -- --grep roads-micro # одна
```

Свой конфиг и **один воркер**: три хромиума с живыми контекстами WebGL
дерутся за то самое CPU, чей бюджет проверяется. В `npm run test:e2e`
эти тесты не входят и в CI не запускаются — десятимиллисекундный бюджет
на общем раннере производит флаки, а не сигнал.

Печатается сводка и по строке на провал:

```
perf 61/64 within budget · worst pass: zoom-bands secondary 8.1ms
NEW   zoom-bands   primary   691.8ms decode  decode ×54 (2307.3ms)
→ e2e/perf/last-run.json
```

`691.8ms decode` — худший одиночный вызов и его фаза; `decode ×54
(2307.3ms)` — самая дорогая фаза за весь проход. Обычно это одно и то
же, а когда нет — это и есть интересный случай.

Всё остальное лежит в `e2e/perf/last-run.json`: каждая студия, каждая
фаза, стены, перцентили, удерживаемые байты. Печатать это в терминал
незачем — оно ждёт там, пока понадобится.

- `PERF_VERBOSE=1` — печатать и успешные строки.
- `PERF_BASELINE=write` — перезаписать `baseline.json` итогом прогона.
- `PERF_GATE=regressions` — ронять прогон только на новых или
  ухудшившихся против `baseline.json` провалах.

`baseline.json` — снимок известных провалов. Репортёр метит каждый
провал `KNOWN` или `NEW` относительно него, так что новая просадка
видна среди старых.
